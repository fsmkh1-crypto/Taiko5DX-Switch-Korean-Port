# AGENTS.md

Operating rules for ChatGPT, Claude, or any other coding/research agent working on this repository.

1. **Mandatory pre-read:** before any analysis, implementation, validation, IPS generation, or crash diagnosis, read `PROJECT_STATE.md`, `docs/VALIDATION_LEDGER.md`, `PATCH_MAP.md`, `docs/INLINE_VALIDATION_POLICY.md`, `docs/PHASE0_FAILURE_MODE_PLAN.md`, `docs/RUNTIME_TEST_RESULTS.md`, and `docs/POST_D5519_ANALYSIS.md` as applicable. For whether a fact must be checked again, `docs/VALIDATION_LEDGER.md` is the first authority.
2. **No redundant revalidation:** reuse `VERIFIED` / `VERIFIED-RUNTIME` ledger facts unless an allowed trigger exists: changed input/version/hash, contradictory evidence, inadequate provenance for a current high-risk decision, or proof that the prior method was unsound. A new chat/model/agent is never itself a trigger.
3. If revalidation is legitimately required, perform it once and record validation ID/date, exact claim, input identity/hash/version, method/script/parameters, offsets/ranges/count units, result/status, and a reproducible artifact/report/commit path.
4. Treat canonical confirmed facts as established unless a new result directly contradicts them or the ledger marks them `VERIFIED-LEGACY` / `NEEDS-REVERIFY` for the decision at hand.
5. **Corrected Phase-0 fact:** the dominant defect in all IPS-bearing builds through P0N v0.2f was the missing Eden NSO-header `+0x100` IPS coordinate shift. P0N2 passes with 5,519 true no-ops, M1A passes with a real inline, and D5519 passes early gameplay with all historical 5,519 real replacements at corrected offsets. Do not repeat old A/B address-halving diagnosis as if those builds patched intended addresses.
6. Optimize for an integrated working Eden mod, not endless isolated validation phases. Runtime success is evidence of route stability, not automatic release-SAFE promotion.
7. When debugging, use feature switches/delta debugging only to isolate a reproducible failure; never infer that a passing split is globally safe.
8. Assume a complete extracted Switch v1.1.3 dump is available locally. Do not redesign around manually supplying one file at a time.
9. Do not commit XCI/NSP/NCA, Switch executables, PC executables, the PC patch archive/payload, fonts, translated game data, keys, dumps, or generated full mod packages.
10. It is acceptable to commit hashes, sizes, Build IDs, offsets, patch bytes, scripts, manifests, and analysis needed to reproduce the port from locally supplied source material.
11. Never replace Switch `CMENU/CWTDAT_JP.TR5` wholesale with the PC version. Reconstruct only validated changes onto the Switch-native base.
12. Do not treat the 17,103 PC EXE replacement records as a single string blob. They are primarily same-length in-place records and must be mapped to Switch homologous locations.
13. At the end of meaningful work, update `docs/VALIDATION_LEDGER.md` for new/revalidated/invalidated facts, plus `PROJECT_STATE.md`, `PATCH_MAP.md` when relevant, and `CHANGELOG.md`.
14. Record failed/superseded approaches briefly so later agents do not repeat them.
15. Prefer implementation plus real Eden testing over speculative micro-analysis when both are possible, but do not bypass mandatory static safety gates for release inline patches.
16. Final end-user frontend is Android APK first. It accepts the user's extracted Switch 1.1.3 dump and PC Korean patch archive and emits an Eden-ready mod through user-granted Android Storage Access Framework locations.
17. Do not create a second patch engine for Android. Stabilize the core builder first, then wrap the same logic.
18. A Windows CLI/EXE may be added later only as a secondary frontend sharing the core logic.
19. **Eden Android storage:** do not assume direct filesystem access to Eden's internal folder. Development instructions use Eden's per-game Add-ons installer (`+ Install` -> `Mods and cheats`) with an extracted mod root containing `exefs/` and/or `romfs/`.
20. Keep `docs/EDEN_ANDROID_TEST_GUIDE.md` aligned with development-build installation/test observations.
21. **Inline-validation invariant:** `unique exact match` is candidate-discovery evidence only, never a release-safety criterion. Final inclusion follows `docs/INLINE_VALIDATION_POLICY.md`.
22. **Full-corpus target:** the release validator ultimately covers all 17,103 T5K inline records. The historical 5,519 exact-unique subset is now a working diagnostic baseline, not a pre-approved release set.
23. **Repeated-object rule:** for short patterns with many raw substring matches, recover actual Switch string objects using field boundaries, pointer/relocation/stride evidence, and replacement-consistent pooling. Never globally replace every raw byte occurrence of `年/日/貫/文/城/はい` or similar short tokens.
24. **Yomi policy:** Korean main names remain translated, original Japanese halfwidth-kana yomi should be preserved internally where possible, and the unnecessary visible yomi/furigana line should be suppressed at its UI call sites. Do not zero internal yomi keys merely to hide the line.
25. **PC context identity gate:** never use a PC executable for RVA-neighborhood/homology evidence unless its size and SHA-256 match the T5K target. File-version text alone is insufficient.
26. **User start gate:** discussion/review/planning does not authorize builds, code modifications, or implementation commits until the user gives an explicit execution signal such as `시작`, `해`, `진행`, or `ㄱㄱ`. One execution signal authorizes only the scope agreed at that moment. After analysis results are reported, a fresh execution signal is required before moving into the next implementation/build stage. A direct documentation request authorizes only that documentation action.
27. **Root-cause-family rule:** do not patch only the single symptom that exposed a defect. Once a root cause or common mechanism is identified, first enumerate every affected data class, code path, call site, runtime descriptor, and analogous visible symptom that could share that cause. Do not create a local fix until the impact surface of that cause family has been surveyed to a reasonable stopping point.
28. **PC-patch-first rule:** when the Windows Korean patch already solves an equivalent behavior, inspect its actual replacement bytes, font strategy, runtime descriptors, pointer handling, and other relevant implementation before inventing a Switch-specific workaround. Reproduce the PC behavior on Switch when structurally appropriate; diverge only when Switch architecture or UX gives a concrete reason.
29. **Analysis-before-modification rule:** keep diagnosis and modification as separate phases. When an analysis phase reaches a conclusion, report the result to the user first with `confirmed / likely / uncertain / rejected hypotheses / affected scope / proposed fix`. Do not automatically continue into code edits, build generation, or commits without a new explicit execution signal.
30. **Diagnostic-build discipline:** a diagnostic build should isolate one root-cause family at a time. Multiple locations that are proven instances of the same mechanism may and usually should be patched together so the family is tested coherently; unrelated hypotheses must not be mixed into the same diagnostic artifact.
31. **Hypothesis invalidation:** when runtime or static evidence disproves or materially weakens a hypothesis, record that result in `docs/VALIDATION_LEDGER.md` and/or `docs/RUNTIME_TEST_RESULTS.md` so later agents do not retry the same local workaround under a different name.
32. **Source-grounded names/encodings:** when a proper name, Korean spelling, compact glyph code, or replacement mapping can be read directly from the PC Korean patch, font, or canonical project data, verify it from that source instead of guessing from Japanese romanization or visual appearance. If source data and runtime display disagree, treat that disagreement as an implementation clue rather than silently changing the intended translation.
