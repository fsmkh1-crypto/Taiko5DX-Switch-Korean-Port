# Build & Runtime Provenance Preservation Policy

This policy is mandatory for every diagnostic build, runtime-validation build, and release-candidate build in this repository.

Its purpose is to prevent a recurrence of builds whose runtime result survives but whose builder, emitted IPS, manifest, exact artifact identity, or reconstruction path is lost.

## 1. Core invariant

A runtime result is useful only when the chain below can be reconstructed:

`source inputs -> exact builder/script commit -> guarded patch plan -> emitted patch -> self-verification -> packaged artifact -> installed/tested artifact -> runtime observation`

Saving only the final ZIP is insufficient. Saving only the builder is insufficient. Saving only a screenshot or chat report is insufficient.

## 2. No untracked/manual diagnostic builds

Every diagnostic or runtime-validation artifact must be generated by a repository-tracked script or builder.

- Do not hand-edit IPS records, ZIP contents, offsets, or patch bytes without capturing the exact operation in a reproducible repository script.
- If a one-off transformation is unavoidable, commit the transformation script or a machine-readable patch manifest before treating the artifact as canonical evidence.
- Human-calculated replacement encodings must not substitute for source-grounded bytes when the PC patch or canonical data contains the real replacement.

## 3. Input identity must be recorded

The build report must record every input identity that can change the result, including as applicable:

- repository commit SHA used to build;
- Switch title/version/Build ID;
- Switch `main` identity/hash when available;
- PC Korean patch archive hash;
- `dinput8.dll` hash;
- T5K resource hash or otherwise exact resource identity;
- source and patched font hashes;
- any base diagnostic/release artifact name and SHA-256;
- any other source binary or data file whose bytes influence the output.

If an expected identity guard fails, the build must stop. Do not adapt offsets or replacement lengths to "make it work".

## 4. Patch-plan provenance

For each emitted patch record, preserve enough information to reconstruct and audit the write:

- semantic module/family;
- source record ID/RVA or other canonical provenance when applicable;
- mapped target offset;
- emitted IPS/IPS32 offset;
- original/preimage bytes;
- replacement bytes;
- original-byte guard result;
- payload length.

For grouped diagnostics, record which records are diagnostic targets and which are already-verified prerequisites.

Silent guard skips are forbidden for diagnostic-control builds. A guard mismatch must fail the build unless the diagnostic design explicitly defines and records a different behavior.

## 5. Emitted-patch self-verification is mandatory

Immediately after writing an IPS/IPS32 artifact, the builder must re-open and parse the file it just emitted.

The builder must verify at minimum:

1. patch envelope/format validity;
2. exact record count;
3. every expected emitted offset;
4. every expected payload byte sequence;
5. mapped-to-emitted coordinate conversion;
6. absence of unexpected extra records;
7. exact round-trip equality between the intended patch plan and reparsed patch records.

If any check fails, the artifact must not be used for runtime testing.

The build report must record the result of this self-verification.

## 6. Required counts and guard census

Each build report must include a machine-readable census appropriate to the build, including:

- intended diagnostic record count;
- prerequisite record count;
- total emitted record count;
- guard-pass count;
- guard-fail count;
- guard-skip count;
- unexpected/extra record count;
- self-reparse/round-trip status.

Counts must use explicit units. Do not write ambiguous totals such as "patterns" when the evidence concerns emitted IPS records.

## 7. Artifact hashes are mandatory

After emission/packaging, compute and record SHA-256 for every runtime artifact that matters to interpretation, including at minimum:

- emitted IPS/IPS32 file;
- final distributed/test ZIP or other installable package.

Where a runtime test uses a base artifact plus a delta artifact, record SHA-256 for both.

A filename without a hash is not sufficient artifact identity.

## 8. Storage split

### Repository

Commit reproducibility metadata and small source artifacts, including:

- builder and diagnostic scripts;
- manifests;
- build reports;
- emit/reparse logs;
- offsets, hashes, byte guards, and patch bytes;
- runtime-result documents;
- validation-ledger and project-state updates.

### Google Drive

Store generated binary/runtime artifacts that are intentionally excluded by `.gitignore`, including:

- test/release ZIP packages;
- raw IPS/IPS32 files when retention is useful;
- large runtime logs, screenshots, and other binary evidence.

Use the project Drive workspace, normally `태합입지전 포팅/Eden_Builds/` for build artifacts and `태합입지전 포팅/Test_Results/` for runtime evidence.

The repository report/manifest must link the Drive artifact by stable filename/path plus SHA-256. A Drive filename alone is not provenance.

## 9. Runtime-test provenance

Every runtime result used as canonical evidence must record, as applicable:

- test/build ID;
- tested artifact filename and SHA-256;
- Eden version/build when known;
- game version/update and Build ID;
- installation procedure;
- whether other add-ons/mods were enabled, disabled, or removed;
- exact route/screen/object observed;
- baseline/control condition where the diagnostic design requires one;
- observed result;
- PASS/FAIL/partial classification and its narrow interpretation;
- screenshot/log identity when retained.

If the emulator's internal installed file cannot be hashed directly, record that limitation explicitly. Do not claim stronger installed-artifact identity than the evidence supports.

## 10. Preserve failed diagnostics too

Failed and invalidated diagnostic artifacts must retain enough provenance to prevent repetition of the same failed hypothesis.

At minimum preserve:

- builder/script and commit;
- build report/manifest;
- artifact hash if an artifact was produced;
- runtime observation;
- invalidated or weakened hypothesis;
- validation-ledger/runtime-results entry when the result changes project knowledge.

Do not preserve only successful builds.

## 11. Missing provenance downgrades evidence

If a historical runtime result lacks the builder, exact artifact hash, emitted-patch record evidence, or sufficient reconstruction path for the decision at hand, do not silently treat it as fully reproducible canonical evidence.

Depending on severity, mark or retain it as:

- observation only;
- `VERIFIED-LEGACY`;
- `NEEDS-REVERIFY`;
- provenance-insufficient for the current high-risk decision.

The missing artifact does not make the observation false. It limits what causal or implementation claims may be derived from it.

## 12. Build report minimum schema

A diagnostic build report should contain at least the following logical fields, adapted to the build:

```text
test_id
repository_commit
inputs
  switch_identity
  pc_reference_identity
  font_identity
records[]
  family
  role (diagnostic/prerequisite)
  source_provenance
  mapped_offset
  emitted_offset
  original_hex
  replacement_hex
  guard_result
counts
  diagnostic_records
  prerequisite_records
  total_records
  guard_pass
  guard_fail
  guard_skip
  extra_records
verification
  self_reparse_exact
  coordinate_roundtrip_exact
artifacts
  ips_filename
  ips_sha256
  package_filename
  package_sha256
  drive_location
```

Fields may be added but must not be omitted when they are relevant to reproducibility.

## 13. Runtime result must point back to build provenance

A runtime-result document must identify the exact build report/manifest and artifact hash that produced the tested package.

The chain must be navigable in both directions:

- build report -> retained runtime artifact;
- runtime result -> exact build report and artifact SHA-256.

## 14. Relationship to existing rules

This policy supplements `AGENTS.md`, `docs/INLINE_VALIDATION_POLICY.md`, `docs/VALIDATION_LEDGER.md`, and the project-state documents.

It does not relax release-safety rules, the user start gate, analysis-before-modification, one-root-cause-family diagnostic discipline, or the requirement to use the real PC Korean patch data instead of guessing.

When a narrower stage-specific policy requires stronger provenance, the stronger rule wins.
